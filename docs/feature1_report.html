1. Executive summary

Feature 1 is PropLock's trust layer. Before a broker's rental ad goes live, it checks the ad against three sources of truth, the owner's verified record, real map routes and state tenancy rules, and only then mints the listing as a PayPal Catalog product with a Verified Commute & Refund Protected badge. Features 2–4 (qualification, escrow hold, invoicing) all rely on that verified record.

AreaStatus
Architecture and code structureGOOD Clean separation of API, agents, services and DB; compiled LangGraph StateGraph with parallel fan-out.
Test suitePASSES 9/9, but tests rely on filename heuristics and fallbacks, so they don't cover the bypasses below.
Trust guaranteesBROKEN Rent/furnishing never compared with the owner (M1); lies in ad text skip the commute check (M2); audit hash doesn't lock broker photos (M4); unauthenticated ground-truth writes (M6).
Failure handlingFAIL-OPEN PayPal failure returns a fake product ID (M5); DB errors swallowed and reports fabricated (M7); commute fallback invents evidence (M3).
ReproducibilityBROKEN requirements.txt lacks sqlalchemy and langgraph (M8).

Recommended fix order: M8 → M1 → M2 → M5 → M3 → M4 → M7 → M6. The first four make the demo honest; the rest make it robust.

Check B: commute truth

Broker says:  "5 min walk to Indiranagar Metro"

No AI or external API is needed: it compares numbers already in your database. It is the cheapest check and catches the most common scam.

M1 Broker claims are never compared with the owner's data

Where: agents/decision_engine.py lines 32–36. Evidence: P1. A broker charging ₹55k (owner agreed ₹35k) and advertising "Fully Furnished" for an unfurnished flat is VERIFIED, and the inflated price is minted into PayPal.

Buggy code

    compliance_audit.verdict == "PASS"
)   # claimed_rent / deposit / furnishing never checked against owner_truth
Fix: add Check D
FURNISH_RANK = {"Unfurnished": 0, "Semi-Furnished": 1, "Fully Furnished": 2}

def check_ground_truth(sub, mandate, owner) -> list[str]:
    issues = []
    if not (mandate.min_rent <= sub.claimed_rent <= mandate.max_rent):
        issues.append(f"Rent {sub.claimed_rent} outside owner range {mandate.min_rent}-{mandate.max_rent}")
    if sub.claimed_deposit > mandate.max_deposit:
        issues.append(f"Deposit {sub.claimed_deposit} > owner-agreed {mandate.max_deposit}")
    if FURNISH_RANK[sub.claimed_furnishing] > FURNISH_RANK[owner.furnishing_status]:
        issues.append(f"Claims {sub.claimed_furnishing}, owner registered {owner.furnishing_status}")
    if sub.brokerage_fee > mandate.max_brokerage_months * sub.claimed_rent:
        issues.append("Brokerage above agreed cap")
    return issues   # non-empty -> FAIL

6. How rental brokers work in real life

Based on common practice in Indian metros (Bengaluru, Chennai, Mumbai, Delhi). Fees and customs vary by city and over time.

  1. Getting the flat. A busy or non-resident owner hands keys to one or more brokers, or to an agency such as "XYZ Properties" that uses sub-brokers.
  2. Advertising. Ads on portals, WhatsApp and Facebook. Several brokers compete for the same flat, so ads get exaggerated.
  3. Handling leads. Dozens of calls a day about availability, deposit, pets, bachelors.
  4. Site visits. Time and fuel spent per visit; many tenants don't turn up.
  5. Closing. Token advance, rent agreement between owner and tenant, deposit to the owner.
  6. Getting paid. A separate brokerage fee, commonly one month's rent (sometimes 15 days), usually from the tenant and sometimes from the owner as well.

8. Fake photo defenses

The audit hash only detects changes after verification. If a broker uploads a web photo at submission, the hash simply locks in the fake. Catching it is Check A's job, and today Check A misses it: no watermark, a harmless filename, a furnished-looking room, and the baseline comparison is discarded.

LayerHowStops a web photo?
0. Show only owner photosThe public listing displays XYZ Properties' baseline photos; the broker writes the text only✅ fully; already half-built
1. Live in-app captureCamera page records GPS and time; reject if > 100 m from the property or older than 30 days✅ strong
2. Same room as baselineGemini compares windows, doors, flooring, room shape; ignores furniture✅ good
3. Reverse image searchGoogle Cloud Vision Web Detection or TinEye API✅ if the photo is online
4. Own pHash databaseSame photo already used for another property✅ reuse across properties
def check_live_capture(meta, owner):
    dist = haversine_m(meta.lat, meta.lng, owner.coordinates.latitude, owner.coordinates.longitude)
    if dist > 100:
        return "FAIL", f"Photo taken {dist:.0f} m from the property"
    if meta.captured_at < now() - timedelta(days=30):
        return "FAIL", "Photo older than 30 days"
    return "PASS", "Captured on-site"

SAME_ROOM_PROMPT = """Image 1 is the owner's verified photo of the empty flat.
Image 2 is the broker's listing photo. Ignore furniture. Compare windows, doors,
flooring, walls, ceiling and room shape. Is this the SAME physical room?
Return JSON: {"same_room": bool, "confidence": float, "mismatched_features": [str]}"""

9. Commission vs rent markup

Brokers do need to earn commission, but in the normal Indian rental market commission is not added into the rent. The rent agreement is signed by owner and tenant, so a hidden markup surfaces at signing or pushes payments outside the lease.

ModelWho paysRent markup OK?
Normal brokerage (separate fee)One-time fee❌ No. Rent goes to the owner.
Asking price vs final priceNobody extra✅ Within the owner's range
Rent-to-rent / master lease / co-livingBuilt into the rent✅ Only with the owner's written consent; operator is the landlord on the lease
Hidden markupHidden in rent❌ This is the bait-and-switch PropLock exists to stop

So Check D compares the listing against an owner-approved range, and commission is declared in its own brokerage_fee field. The tenant then sees the true move-in total: rent + deposit + brokerage_fee. Brokerage norms are market practice, not law; present them as agency policy in the app.

Commute: who is the referee?

Commute claims are checked with the Maps API, not against the owner. The owner supplies only the origin (verified coordinates); the broker supplies the claim; Maps is the referee. The weak spot is the origin itself: capture GPS at key handover, or geocode the registered address and reject a pin more than ~200 m away.

10. Target architecture (all fixes applied)

Key design decisions

  1. Three-state results. Every check returns PASS, FAIL or UNVERIFIABLE with evidence and its source. A missing key or timeout never becomes PASS, and never an invented "LIE".
  2. Check D. Deterministic comparison with the owner mandate; cheapest check, most common scam.
  3. Claim extraction first. The LLM reads the ad; deterministic code judges it.
  4. Human review via LangGraph interrupt() with a checkpointer, implementing the blueprint's "Fix or manual review" branch.
  5. Signed, versioned audit. Canonical JSON → HMAC; GET /audit/{id} returns exactly what was signed and /verify recomputes it.
  6. Outbox for PayPal. Commit first, then mint with a deterministic product ID and PayPal-Request-Id; retries are safe and nothing is orphaned.
  7. Rules as data. Caps in a versioned file with effective_date and source_url; retrieval only shows the clause text.
  8. Roles. MANAGER writes ground truth and mandates, BROKER submits listings, PUBLIC reads verified listings.

Appendix B. Caveats on legal figures

The legal figures in the current code and knowledge files should be verified against official gazette texts before the demo. The reviewer's understanding (not independently verified): the Karnataka Rent Act caps advance at 10 months (Section 11) rather than 2–3 months; the Model Tenancy Act 2021 caps residential deposits at 2 months; the 6-month Karnataka ceiling is a platform policy, not law. tamil_nadu_tenancy_2019.md contains a contradictory clause ("null, void, and enforceable"). Brokerage figures (1 month, 15 days) are market practice, not statute.
